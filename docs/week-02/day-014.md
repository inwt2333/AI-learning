## 1. 实验设计

要回答三个问题：

1. **链路**：Day 011–013 的公式能否组装成一个端到端的搜索器？
2. **对比**：BM25 与 TF-IDF 余弦在同一语料、同一评价集上差多少？
3. **失效**：这个系统在哪些真实查询上会坏，为什么？

两条数据流如下。索引阶段一次完成，查询阶段只走第二条：

```
索引阶段（离线，一次）：
12 篇已分词文档
  → 逐篇统计词频 → 倒排索引（词 → 文档 → tf）
  → 记录文档长度、平均长度 avgdl
  → 记录每个词的文档频率 df

查询阶段（在线，每次）：
查询字符串
  → 按空格切分（真实系统用第 1 周的 Tokenizer）
  → 查倒排索引，只取命中文档
  → BM25 逐词累加打分（k1=1.2, b=0.75）
  → 按分数排序返回
```

对比基线是 Day 011 的 TF-IDF 余弦（经典 IDF、原始计数 TF、余弦打分），实现沿用当天代码，只做接口对齐。

## 3. 倒排索引：从扫描到查找

Day 013 的 `bm25_score` 对每篇文档从头扫描。真实检索反着来：**从词出发找文档**。倒排索引（inverted index）就是"词 → 出现该词的文档及其词频"的映射：

```python
from collections import Counter
from math import log

def build_index(docs):
    """倒排索引：词 → {文档编号: 词频}，另存文档长度与全局统计。"""
    postings = {}
    doc_lens = []
    for doc_id, doc in enumerate(docs):
        doc_lens.append(len(doc))
        for token, tf in Counter(doc).items():
            postings.setdefault(token, {})[doc_id] = tf
    df = {token: len(p) for token, p in postings.items()}
    return {
        "postings": postings,
        "doc_lens": doc_lens,
        "avgdl": sum(doc_lens) / len(doc_lens),
        "df": df,
        "N": len(doc_lens),
    }

index = build_index(docs)
print(f"|V| = {len(index['postings'])}，N = {index['N']}，avgdl = {index['avgdl']:.4f}")
for token in ("自然语言", "神经网络", "人工智能", "概率"):
    print(f"postings[{token!r}] = {index['postings'][token]}  df = {index['df'][token]}")
```

输出：

```
|V| = 69，N = 12，avgdl = 7.8333
postings['自然语言'] = {0: 1, 7: 1}  df = 2
postings['神经网络'] = {2: 1, 6: 1}  df = 2
postings['人工智能'] = {1: 1, 9: 1}  df = 2
postings['概率'] = {4: 1, 10: 1, 11: 4}  df = 3
```

注意 postings 的三个身份：查询时的**入口**（不用扫全库）、词频的**存储**（tf 已在索引里）、文档频率的**来源**（df 就是每个 posting list 的长度）。打分需要的一切统计量都在索引里，这是 Day 078 一切工程优化的起点。

## 4. 检索函数：BM25 与基线

BM25 打分直接在索引上累加，公式与参数含义见 Day 013，这里只换计算方式：

```python
def idf_bm25(token, index):
    df = index["df"][token]
    return log((index["N"] - df + 0.5) / (df + 0.5) + 1)

def bm25_search(query, index, k1=1.2, b=0.75):
    """只遍历命中文档：分数从 posting list 累加，不扫描全库。"""
    scores = {}
    for token in query:
        if token not in index["postings"]:
            continue  # 词表外查询词跳过（Day 011 的 OOV 约定）
        weight = idf_bm25(token, index)
        for doc_id, tf in index["postings"][token].items():
            length_ratio = index["doc_lens"][doc_id] / index["avgdl"]
            saturation = tf * (k1 + 1) / (tf + k1 * (1 - b + b * length_ratio))
            scores[doc_id] = scores.get(doc_id, 0.0) + weight * saturation
    return sorted(scores.items(), key=lambda pair: -pair[1])
```

TF-IDF 余弦基线沿用 Day 011 的实现（经典 IDF、原始计数 TF、余弦），为了进同一套评价函数，返回值统一为 `(文档编号, 分数)` 列表：

```python
def tfidf_vector(tokens, index):
    counts = Counter(tokens)
    return {
        token: tf * log(index["N"] / index["df"][token])
        for token, tf in counts.items()
    }


def cosine(vec_a, vec_b):
    dot = sum(vec_a[t] * vec_b.get(t, 0.0) for t in vec_a)
    na = sum(w * w for w in vec_a.values()) ** 0.5
    nb = sum(w * w for w in vec_b.values()) ** 0.5
    return dot / (na * nb) if na and nb else 0.0


def tfidf_search(query, docs, index):
    query_vec = tfidf_vector(query, index)
    scored = [
        (i, cosine(query_vec, tfidf_vector(doc, index)))
        for i, doc in enumerate(docs)
    ]
    return sorted(scored, key=lambda pair: -pair[1])
```

两个返回格式一致的检索器，共用一套评价代码——**对比实验的第一条纪律是：除被比较的方案外，一切保持相同**。

## 5. 评价指标：Recall@K 与 MRR

对排名列表与相关文档集合 $$R$$：

$$
\operatorname{Recall@}K=\frac{\left|\,\operatorname{top}\text{-}K\cap R\,\right|}{|R|}
$$

衡量前 $$K$$ 条结果覆盖了多少相关文档。MRR（Mean Reciprocal Rank，平均倒数排名）先对每条查询取**第一个相关文档**的排名倒数：

$$
\operatorname{RR}(q)=\frac{1}{\operatorname{rank}_{q}^{\text{first}}}
$$

再对所有查询取平均（无相关文档命中则该查询记 0）。它衡量"用户要多翻几条才碰到第一个对的"。

用本实验的堆词查询手算：查询"概率"，返回 top-3 为 doc11（堆词）、doc4、doc10，相关集合 $$R=\{4,10\}$$。于是 $$\operatorname{Recall@}3=2/2=1.0$$，但第一个相关文档排在第 2 位，$$\operatorname{RR}=1/2=0.5$$。**同一个查询，覆盖满分、首命中减半**——两个指标看的不是一件事。

## 6. 结果与分析

评价代码与运行结果：

```python
def recall_at_k(ranked, relevant, k=3):
    top = {doc_id for doc_id, _ in ranked[:k]}
    return len(top & relevant) / len(relevant)


def reciprocal_rank(ranked, relevant):
    for rank, (doc_id, _) in enumerate(ranked, start=1):
        if doc_id in relevant:
            return 1 / rank
    return 0.0


def evaluate(search_fn, eval_set):
    recalls, rrs = [], []
    for query, relevant in eval_set:
        ranked = search_fn(query)
        recalls.append(recall_at_k(ranked, relevant))
        rrs.append(reciprocal_rank(ranked, relevant))
    return sum(recalls) / len(recalls), sum(rrs) / len(rrs)


r_bm, m_bm = evaluate(lambda q: bm25_search(q, index), eval_set)
r_tf, m_tf = evaluate(lambda q: tfidf_search(q, docs, index), eval_set)
print(f"BM25        : Recall@3 = {r_bm:.4f}, MRR = {m_bm:.4f}")
print(f"TF-IDF 余弦 : Recall@3 = {r_tf:.4f}, MRR = {m_tf:.4f}")
```

输出：

```
BM25        : Recall@3 = 1.0000, MRR = 0.9167
TF-IDF 余弦 : Recall@3 = 1.0000, MRR = 0.9167
```

逐查询对照：

```
逐查询对照（top-3 文档编号）：
  '自然语言 处理'      相关=[0, 7]  BM25=[0, 7]  TFIDF=[0, 7, 1]
  '神经网络'         相关=[2, 6]  BM25=[2, 6]  TFIDF=[2, 6, 0]
  '人工智能'         相关=[1, 9]  BM25=[1, 9]  TFIDF=[1, 9, 0]
  '语言 模型'        相关=[4, 10]  BM25=[4, 10, 0]  TFIDF=[4, 10, 0]
  '检索 文档'        相关=[5]  BM25=[5]  TFIDF=[5, 0, 1]
  '概率'           相关=[4, 10]  BM25=[11, 4, 10]  TFIDF=[11, 4, 10]
```

三个发现，一个比一个重要：

**发现一：两个方案在本评价集上不可区分。** 六条查询的 top-3 完全一致，指标一字不差。这**不是**"BM25 没用"：Day 013 已在受控对比里展示过两者的行为差异（长度处理哲学不同、堆词幅度不同）。本语料是短而干净的文档，没有触发那些差异的条件（没有多主题长文档、没有跨字段的词频冲突、没有部分命中的多词查询）。结论只能写成："在本集上不可区分"——评价集的**区分度**决定了实验能回答什么问题。

**发现二：唯一的失分来自堆词文档，且指标精确量化了它。** 查询"概率"下 doc11 抢到第一位，把两个本应排前的相关文档压到第 2、3 名，MRR 从本可到的 1.0 掉到 0.9167（第 5 节手算的 RR=0.5 平均进六条查询）。看分数幅度：

```
堆词查询 top-3 分数对比（query = 概率）：
  BM25   doc11 = 2.033422
  BM25   doc4 = 1.300864
  BM25   doc10 = 1.178802
  TFIDF  doc11 = 0.619401
  TFIDF  doc4 = 0.262970
  TFIDF  doc10 = 0.196989
```

BM25 下堆词文档只领先最近相关文档约 1.56 倍，TF-IDF 余弦下约 2.36 倍——与 Day 013 的结论一致：饱和**压缩**了堆砌的优势，但没有**翻转**排名。指标的价值在这里显形：没有 MRR，"堆词文档排第一"只是一句观察；有了 MRR，伤害变成可跟踪、可回归的数字。

**发现三：Recall@3 = 1.0 不代表系统没问题。** 同一组结果里 MRR 已经失分。只看一个覆盖率指标会漏掉排序质量问题——这也是为什么第 92 天要引入更多指标（NDCG 等）。

## 7. 参数网格与"平表格"的教训

对 $$k_1\in\{0.5,1.2,2.0\}$$、$$b\in\{0,0.5,0.75,1\}$$ 做网格搜索：

```
参数网格（6 个查询，结果仅演示流程）：
   k1     b  Recall@3     MRR
  0.5   0.0    1.0000  0.9167
  0.5   0.5    1.0000  0.9167
  0.5  0.75    1.0000  0.9167
  0.5   1.0    1.0000  0.9167
  1.2   0.0    1.0000  0.9167
  1.2   0.5    1.0000  0.9167
  1.2  0.75    1.0000  0.9167
  1.2   1.0    1.0000  0.9167
  2.0   0.0    1.0000  0.9167
  2.0   0.5    1.0000  0.9167
  2.0  0.75    1.0000  0.9167
  2.0   1.0    1.0000  0.9167
```

十二组参数，指标纹丝不动。这张**平表格**是本实验最有价值的负结果：

* 调参的前提是评价集对参数**敏感**。当所有参数都拿同样的分数，网格搜索只是在测量评价集的无效，不是在测量参数的好坏；
* 能区分方案的评价集需要：多词部分命中查询（长查询）、相关与不相关文档共享词的混淆对、长度差异大的文档、分级相关性标注。构造这些"难例"本身就是检索工程的日常工作（Day 095 的评价集建设展开）；
* 在 6 条查询上选出"最优参数"再报告，是把噪声当信号——正确做法是承认不可区分，扩充评价集后重测。

## 8. 失效案例归因

两类真实失效，都返回空结果，但成因完全不同：

```
失效案例：
  分词不一致 query ['人工', '智能'] → []
  词汇鸿沟   query ['NLP'] → []
```

**分词不一致**：语料里是"人工智能"一个词，查询被切成"人工"+"智能"两个词，两个 Token 都不在词表里。这是第 1 周结论的检索版：**查询侧与索引侧必须使用同一个 Tokenizer**（Day 002、Day 006 的规范化约定在这里变成硬性工程要求）。修法在系统层：查询进来先走与建索引相同的分词器。

**词汇鸿沟**：查询"NLP"，语料通篇是"自然语言"。Token 在词表外，BM25 无从打分。这不是 bug，是词袋方法的边界（Day 011、Day 013）：修法包括同义词扩展、查询改写（Day 088），根本解法是混合检索引入语义向量（Day 083）。

两类失效在指标上都会表现为"相关文档没进前列"，但如果只看指标不做逐例归因，就会把"分词器接错了"这种工程错误误诊为"算法不行"——归因先于优化。

## 9. 边界与工程权衡

* **规模**：本实现把索引放在内存 dict 里，查询复杂度约为"命中 posting 长度之和"。真实引擎要处理持久化、增量更新、分片与压缩（Day 078）；十几篇文档的实验不要外推性能结论。
* **标注质量**：二值、单人的标注撑不起统计结论。正式评价集要多人标注、算标注一致性，相关性分级（Day 092）。
* **平分顺序**：分数相同的文档（如 doc0 与 doc7）谁排前面由排序稳定性决定，实现不同顺序可能不同——报告排名时要意识到这一点。
* **查询侧管线**：真实查询是原始字符串，要经过规范化、分词、停用词决策（第 1 周）；本实验直接接收空格切分的 Token，是为了把变量控制在打分函数上。
* **可复现性**：数据、标注、参数、代码版本固定，是第 13 天"报告必须写清变体"的评价侧对应物。

## 10. 常见误区

### 误区一：指标相同说明两个方案一样好

只能说"在本评价集上不可区分"。换一个有区分度的集合，结论可能不同；把这句话写进实验报告才算合格。

### 误区二：Recall@3 满分就万事大吉

本实验 Recall@3 = 1.0 的同时，堆词文档霸占首位的伤害由 MRR 暴露。单一指标必然盲视，至少覆盖 + 首命中各看一个。

### 误区三：在六条查询上调参

平表格已经说明一切。小集合上的"最优参数"是噪声，扩充评价集前不报告任何调参结论。

### 误区四：把失效案例当 bug 修

分词不一致是工程接线问题（修管线），词汇鸿沟是方法边界（换方法或混合方案）。错误归因会让修复方向整个跑偏。

### 误区五：评价集标注可以随手标

标注是评价集的地基：标错的相关文档会系统性地惩罚正确结果。正式实验需要标注规范、双人标注与一致性检查（Day 095）。

### 基础题 1：手算 MRR

三条查询的首个相关文档排名分别为第 1、第 4、未出现。计算 MRR。

<details>

<summary>参考答案</summary>

$$\operatorname{MRR}=(1/1+1/4+0)/3=(1+0.25+0)/3=0.4167$$（保留四位小数）。未命中的查询记 0 而不是跳过——分母是查询总数。

</details>

### 基础题 2：手算 Recall@K

某查询相关文档为 $$R=\{4,10\}$$，系统 top-3 为 $$\{11,4,10\}$$。计算 Recall@3；若 top-3 为 $$\{11,4,0\}$$ 呢？

<details>

<summary>参考答案</summary>

第一种：$$|\{4,10\}\cap\{11,4,10\}|/2=2/2=1.0$$。第二种：$$|\{4,10\}\cap\{11,4,0\}|/2=1/2=0.5$$。分母是相关文档总数，不是返回条数。

### 进阶题 4：代码审查

下面的实现有什么问题？

```python
def reciprocal_rank(ranked, relevant):
    for rank, (doc_id, score) in enumerate(ranked):
        if doc_id in relevant:
            return 1 / rank
    return 0.0

def recall_at_k(ranked, relevant, k=3):
    top = {doc_id for doc_id, _ in ranked[:k]}
    return len(top & relevant) / len(top)
```

<details>

<summary>参考答案</summary>

`enumerate(ranked)` 从 0 计数，第一个命中会返回 1/0（ZeroDivisionError）；应 `enumerate(ranked, start=1)`。Recall 的分母写成 `len(top)`（返回条数）：返回不足 $$K$$ 条时被高估，且定义应为相关文档总数 $$|R|$$。两个错误都会让指标失真且不易察觉——评价代码本身要有单元测试（如本题的手算用例）。

</details>

### 面试追问 5：Recall@K 和 MRR 各适合什么场景

Recall@K 看覆盖，适合召回层（RAG 取证、候选生成——漏了正确文档后面全白搭）；MRR 看首命中，适合问答与点击型搜索（用户只看第一条）。缓存与推荐场景还看 MRR@10 之外的 NDCG（分级相关，Day 092）。回答时最好带一句：指标选择由用户行为决定，不是随便挑。

### 面试追问 6：这个玩具搜索器到生产还缺什么

分词一致性管线（查询侧与索引侧同一 Tokenizer）；索引持久化与增量更新；查询理解（改写、纠错、停用词）；混合检索与重排（稠密向量、cross-encoder）；在线指标与日志回流（点击、停留）；A/B 与回归测试。每一条都能展开成一天的深题（Day 078–089 覆盖大半）。
